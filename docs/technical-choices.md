# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons.

| Topic | Choice | Reason |
|---|---|---|
| Language core | Lexer, parser, checker and interpreter of the learner's language in Rust, compiled to WebAssembly with `wasm-bindgen` | The owner's choice, and a language implementation is where Rust's enums and exhaustive matching help most. The whole core stays a plain Rust library, tested with `cargo test` without a browser; only a thin crate exposes it to JavaScript. |
| Execution | The interpreter runs one instruction per `step()` call, driven by the interface at each animation frame, a number of steps per frame set by the speed | An infinite loop of the learner never freezes the page: it keeps running visibly until **Pause** or **Reset**. The same mechanism gives the animation of the robot, the highlighted current line, the pause, the step button and the breakpoints. |
| No panic in the core | Clippy lints that forbid what can panic in the core (`unwrap`, `expect`, indexing, `panic!`), set up with the workspace | A panic aborts the WebAssembly module, and the page with it: every program of a learner, even absurd, must end with an error the interface can show. Taken from rust-exile-market, whose parser follows the same rule. |
| Interface | TypeScript with [Svelte](https://svelte.dev) 5 | A component holds its markup, script and style in one file with little boilerplate, so the repository reads easily; the runes (`$state`, `$derived`) make the reactive values explicit; compiled, with almost no runtime next to the WebAssembly module. React was rejected for its boilerplate and the pitfalls of its hooks, Vue for being a little more verbose, Solid for its smaller community. |
| Pages | [SvelteKit](https://svelte.dev/docs/kit) with `adapter-static`, server-side rendering off, the pages prerendered as empty shells | The specifications have four kinds of pages (home, level, sandbox, manual), each with its own address so that the manual can be linked: SvelteKit gives the routing and the folder layout every Svelte developer knows, and builds a static website. Svelte with Vite and a router of our own was rejected: less code at first, but a structure of our own to explain. |
| Interpreter | The checked tree is translated once into a flat list of instructions, each with its place in the source, in `crates/core/src/interpreter/` (`compiler.rs` writes them, `machine.rs` runs them up to the end of a step, `memory.rs` holds what each of them changes, `value.rs` and `operators.rs` the values and what the operators compute); the machine owns them and keeps an explicit stack of frames (each frame: its function, its next instruction, its variables, its line, and where its own values start among those of the expressions being evaluated), never the Rust call stack; an instruction marks the start of each line, where a step ends, and a step also ends when a function ends, on the line of its call; a function is translated where it is defined, the main program jumping over it; a call leaves its result, a value or none, apart, where the expression around it takes it, for the built-in functions as for the others; each variable keeps the number of the step that wrote it last, which is how the variables panel knows the ones the last step changed; the translation is the only recursion, on a tree whose depth the parser limits | Pausing between two steps, anywhere in nested loops and calls, needs the whole state of the program in data, and the variables panel reads that same data. A step also ends in the middle of an expression, when a call is entered (`let total = double(3) + 1`): a machine that walks the tree would keep references into it, which the bridge can't hold from one animation frame to the next without counting the references of every node (the parser, the checker and their tests rewritten) or leaking the tree at each **Run**; a list that the machine owns resumes at its next instruction (decided on 2026-11-12, instead of walking the tree). The limit of 200 nested calls is the length of the stack of frames: a recursion of the learner can't overflow the stack of the browser. The state of the machine says whether the line highlighted is resumed after a call: only the machine knows it, and a breakpoint pauses once per line run (decided on 2026-11-13). The interface can't find the variables changed by a step by itself: at the speed **Instant**, it would copy them all before each step. |
| Lexer | Hand-written, line by line, in `crates/core/src/lexer.rs`: the indentation becomes `Indent` and `Dedent` tokens (four spaces more, or back to an enclosing line, anything else is an error that names the two closest levels); the comments are dropped, the place of each comment line being kept aside, so that the parser tells a block of comments from an empty one; any word of letters, digits and underscores, in any alphabet, is a name; the first error stops it | A statement never spans two lines, so reading line by line is enough and keeps the lexer short; no generator (`logos`) for a few dozen tokens. Whether an indented line follows a `:` is left to the parser, which can then say that the `:` is missing on the line above rather than that the next line is indented. Names in any alphabet (`paintSide`, `côté`) are refused by the checker, which recalls the rule of the names without writing the name for the learner, rather than by the lexer, which could only say that a character is unexpected. The highlighting of the editor is decided at step 16. |
| Parser | Hand-written, by recursive descent, in `crates/core/src/parser.rs`: one method per statement, and for the expressions a loop that climbs the priorities of the operators; the tree of `crates/core/src/ast.rs` keeps the span of every node, the one of a statement that opens a block being its line up to the `:`, which is the current line shown while the program runs; an `if` holds the list of its branches, so that a long chain of `else if` doesn't deepen the tree; the first error stops it, the lexer's or its own, as one `SyntaxError`; the tree is at most 200 levels deep (parentheses, operators, calls and blocks), the height of each expression being counted as it is built, and the blocks alone nest at most 50 deep | A language this small needs no generator, and a hand-written parser chooses its errors: `=` for `==`, chained comparisons, the words of other languages wherever they are. The depth is limited in the tree, not only in the recursions of the parser: a chain such as `1 + 1 + 1 + …` is parsed by a loop, yet gives a tree as deep as it is long, which would overflow the stack later, in the checker, the interpreter or when the tree is freed. What needs the names of the program (an expression alone on its line that isn't a call, a `break` outside a loop, a function in a block) is left to the checker, which gives every error rather than the first. Measured in the review of step 6a, at 199 levels: the parser alone needs between 64 and 128 KiB of the stack in a release WebAssembly module (between 256 and 512 KiB in a debug one), out of 1 MiB by default; the checker and the interpreter will walk the same tree, so the measure is redone at step 6c, with the blocks. A level of blocks costs more of the stack than a level of parentheses: measured in the review of step 6b, 199 nested `if` needed between 832 and 864 KiB in a debug WebAssembly module (between 384 and 512 KiB for the parentheses), too close to the 1 MiB of the stack, hence the limit of 50 for the blocks, which nobody reaches by hand: four times fewer levels of blocks. Measured again at step 6c in WebAssembly, by linking a module with smaller and smaller stacks until it traps, on the worst case, 50 blocks around an expression of 150 levels: parsing it then freeing its tree needs between 608 and 624 KiB in a debug module (between 144 and 160 KiB in a release one), against 528 to 544 KiB (112 to 128 KiB) for the deepest expression alone, so at least 400 KiB of the default 1 MiB stay free in the debug module that `npm run dev` and `npm test` load. The checker and the interpreter walk the tree after the parser has returned, each with its own need, to measure with them; step 10 tests the whole through the real module. |
| Checker | A walk of the syntax tree, in `crates/core/src/checker.rs`, `check(&Program)` giving every error in the order of the source, each a code with its values and its place, as those of the lexer and the parser; where a statement stands (top level, function, loop) is a small value passed down the walk, not a state to restore; a name refused for its form is still taken as declared, a reserved name never is and keeps its one error, as a parameter too, and a function in a block is still checked as a function; the built-in functions and the colors are enums of the core (`builtin.rs`, `color.rs`), which the interpreter and the map reuse, the variables are a stack of open blocks (`checker/scope.rs`), each with the variables declared so far and, read when the block opens, the `let` written in it, plus the variables whose block has ended: a name that isn't a variable there is then one declared further down, one whose block has ended, or unknown, in that order; a function is checked with a stack of its own, the one around it being put aside, and a first pass lists the variables of the main program, wherever their `let` is, to tell a function that uses one; another first pass lists the functions of the program (`checker/functions.rs`), those written in a block included, each with the place of its name and the number of its parameters, the first of a name being the function: a call is above its definition when its place in the source is before that name, which needs no state in the walk and lets a function call itself; a name that a function has is never a variable, so the walk asks the functions before the variables; and every list of words of the language (keywords, words of other languages, built-in functions, colors) is defined by one macro, `word_enum!` | Unlike a syntax error, an error of names doesn't prevent reading what follows, so the learner sees them all at once; taking a refused name as declared keeps one mistake from giving several errors. An error says what the checker knows of the name, never what the learner meant: reading and changing a variable out of its scope give the same error, and only a name that is nowhere tells a read from a change. A name changed without `let` is not taken as declared, unlike a name refused for its form: nothing says that a `let` was meant, so every use of the name keeps its error, each a fact, and a later error would otherwise give the line of a `let` that doesn't exist. A call of a name is a variable called only when that variable exists there: out of its scope, the checker doesn't know that the variable was meant, and says that no function has this name. Every error of a call is on the name of the function, the wrong number of values included: the tree keeps the place of an expression with the parentheses around it, not the one of the call alone. A name that a function has stays the function, so a variable that takes it has an error at each line that uses it as a variable, and the calls of a second function of the same name are checked against the first: each line is a fact, and they all go away with the one name that is changed. The macro lists each word once, with its variant: written by hand, a word could be forgotten in the list of all of them or in one of the two conversions, and four enums repeated the same code. A crate (`strum`) was rejected for so little. |
| World | The map and the robot in `crates/core/src/world.rs`, a plain Rust model without `serde`: a `Map` of cells, each a wall or a floor with its paint, its item and its passages east and south (the ones north and west being those of its neighbors, so that each passage is kept once, as a boolean), the coordinates as `u8` from the top left; a `Robot` with its direction, the item it carries and one `Option<Tool>`, the brush with its color or the eraser; a `World` that holds both and changes only through the methods of the actions of the built-in functions, which return a `RobotError` (the bump, the item missing or already carried, the robot's state checked before the cell), its sensors being methods too; a level is built with the methods of `Map`, which take the size asked as it is written (so that an error gives it whole) and refuse a paint, an item or the robot on a wall, a wall on a cell that has a paint or an item (the walls are set first, and nothing is lost in silence), and a passage between two cells that aren't both painted | The interpreter (step 9) only calls a method for each built-in function, and the rules of the brush and the eraser are tested without a program. A passage has no color of its own, since each cell draws its half in its own color (decided on 2026-11-12): a boolean is enough, and the rule that a painted passage joins two painted cells is kept by the map alone, by erasing the passages of a cell with its paint. One `Option<Tool>` rather than two booleans makes a brush and an eraser down together impossible to write. |
| Positions | A line and a column, both from 1, the column in characters (Unicode scalar values), at the start and the end of each token and error | The console shows a line and a column as a learner counts them, accents included. CodeMirror counts in UTF-16 code units, where an emoji takes two: the bridge converts with the source (step 10). |
| Numbers | `i64` with checked arithmetic (`checked_add`…), sent to the interface as text | An overflow becomes the error of the specifications instead of a panic or a wrong value; JavaScript numbers can't hold every `i64` exactly. |
| Code editor | [CodeMirror 6](https://codemirror.net) | Every part of its look is set by our own CSS theme, and its extensions already cover what the editor needs: our highlighting (which can come from the Rust lexer), the errors underlined with their message, the current line highlighted, the breakpoints in the gutter, the automatic indentation, undo and search, and the command menu of Ctrl+Space (its `autocomplete` extension groups the suggestions in sections, shows a description next to each, and inserts snippets with fields to fill in). Writing our own editor was rejected: weeks to reach a real editor (cursor, selection, undo, accents, accessibility) and many bugs, outside the subject of the project. Monaco was rejected: several megabytes and hard to take out of its VS Code look. The console, where the program writes, is our own Svelte component. |
| Interface translations | [Fluent](https://projectfluent.org) with `@fluent/bundle`, `locales/en.ftl` as the reference | English only in version 1, French possible later without touching the code. The core returns its errors as a code with its values and its position, never as a sentence, so that the error messages are translated with the rest of the interface. |
| Manual | One Markdown file per section and per language (`manual/en/`), turned into pages when the website is built | Long texts with examples read and change better as Markdown than as Fluent messages; a French manual is another folder. The examples are checked by the tests with the real parser, so that the manual never shows code Stepwise refuses. |
| Levels | TOML files with a format version, one per level in `web/levels/`, named after the stable name of the level in kebab-case (`paint-a-square.toml`), plus `sandbox.toml`: the starting code and the terrain written as they are in literal strings over several lines (`'''`), the terrain one character per cell (`#` a wall, `.` a floor); the robot, the items and the goals placed by coordinates `[x, y]` (origin at the top left, `y` downward); a paint, at the start or in a goal, as a stroke, a color along a path of cells next to each other, which paints the passages between two cells that follow each other; up to three maps one under the other in the file, each with all its content, only the starting code being shared; read with `serde` and `toml` in `crates/core/src/level/`: the schema of the file (`file.rs`, the unknown fields refused) apart from the building of what it describes (`build.rs`, with the methods of `Map`), the goals and the strokes (`goals.rs`, `stroke.rs`) checking their own rules in their constructors without knowing the file: a map of a level has goals, not all of them met before the program runs, and no more items needed than it has; the version stays 1 until the first release, since the files are deployed with the code that reads them; the texts of a level (title, goal, hint) are Fluent messages named after it (`level-paint-a-square-title`), the prefix keeping them apart from those of the interface; the order of the levels and their chapters will be one list, `web/levels/chapters.toml` (step 21), the file of a level knowing nothing of its chapter | The terrain and the starting code, the parts read the most, are written as they will be drawn and typed, without quotes nor escapes, and a comment can say what a variant changes: JSON has neither strings over several lines nor comments, and refuses a comma after the last element. Compared on 2026-11-12, and rejected: JSON (the starting code as an array of lines, `\"` to escape), JSON5 (comments, but no strings over several lines), YAML (implicit types, the indentation, a Rust crate no longer maintained), RON and KDL (little known, KDL without `serde`), Markdown (pleasant to read, but no data: the goals would need a convention of our own, so a format of our own in disguise, and the texts would leave Fluent), the format of the Tiled editor (verbose for our maps) and a format of our own (one more parser). A path rather than cells gives the passages that the strokes at the start and the marks of the goals draw; the goals look at the cells only. One list of the order rather than chapter folders or a chapter written in each level: a folder is listed in alphabetical order and a field gives no place in the chapter, so either would need that list anyway and say the chapter twice. Weight, measured on 2026-11-12 after `wasm-bindgen` in release: the language alone (parser and checker) is 80 kB (33 kB gzipped), 328 kB (130 kB) with the reader of the levels, against 205 kB (88 kB) in JSON; `serde` and the parser weigh, not our code, and the messages of the errors left out save 2 kB. Accepted: about 100 kB gzipped, loaded once and kept in the cache, one reader of the format and its checks in one place. Reading the TOML in TypeScript (`smol-toml`) and handing the maps to the core through the bridge would keep the module light, at the cost of two readers of the same format; it stays possible without changing the files. Every level file is checked by `cargo test` (`crates/core/tests/level_files.rs`), its starting code by the lexer, the parser and the checker; a solution of each variant is run once the interpreter exists. |
| World elements | SVG drawings, designed one by one on a sheet of elements, then used as they are by the application: one file per element in `docs/mockups/world-elements/daylight/`, stacked in each cell (the floor or the wall with its rim and its edge, the paint, the goal marks, the item, the robot turned to its direction with the item in its bay, its pincer and its eyes, the flag of a goal not met); only the paint strokes, which depend on the painted passages, are drawn by the map, in the shades of [Look of the world](../specs.md#look-of-the-world) | Sharp at every size and zoom; the drawings of the mock-up become the files of the application. The map is drawn in SVG too, one Svelte component per element: a map has at most 16 × 12 cells, a few hundred shapes, far below what makes SVG slow; the moves are CSS transitions. A canvas was rejected: it would redraw by hand what SVG and CSS give, and blur at some zooms unless handled. Small files stacked, rather than one drawing per state (a robot carrying, a robot lit…), keep the number of files small and let the animations move each part on its own. |
| Font of the name | Fredoka 600, under the SIL Open Font License, bundled with the application rather than loaded from Google Fonts | Its round shapes answer the corners of the robot and the round ends of the paint. Bundled, the website loads no font from another server, and works the same offline. The fonts of the interface come with the design system. |
| Data | Everything in the browser: a static website, the progress in `localStorage` | No account and no server to run, keep or secure; the learners' data never leaves their browser. |
| WebAssembly build | `cargo build --target wasm32-unknown-unknown`, then the `wasm-bindgen` command-line tool at the exact version of the `wasm-bindgen` crate, from an npm script | The rustwasm organization was wound down in 2025 ([Rust blog](https://blog.rust-lang.org/inside-rust/2025/07/21/sunsetting-the-rustwasm-github-org)): `wasm-bindgen` moved to its own organization and goes on, while `wasm-pack` passed to a single maintainer. Calling `wasm-bindgen` directly avoids depending on `wasm-pack`, with one command more. Checked again on 2026-11-10 (step 4b): `wasm-bindgen` 0.2.130 is its latest version, and `wasm-pack` is still released (0.15.1), but the direct call is kept: one tool less, and `web/scripts/build-wasm.ts` checks the version of the tool against the one of the crate, given by `cargo pkgid`, before building. The glue is generated with `--target web`: Vite loads the module as any other file, without a plugin. |
| WebAssembly size | The release profile at the default `opt-level` 3, with `lto` and one codegen unit, not stripped by Cargo; `wasm-bindgen` removes the name and producers sections | Measured on 2026-11-10 (step 4c) on the probe, after `wasm-bindgen`, with the speed of `step()` called in a loop from Node.js 24: `opt-level` 3 gives 16.3 kB (7.3 kB gzipped) and 206 million steps per second, `"s"` 17.9 kB (7.8 kB) and 186 million, `"z"` 18.1 kB (8.0 kB) and 120 million. On a code this small, 3 is both the smallest and the fastest: it inlines and then removes what `"s"` and `"z"` keep as calls. `strip = true` made `wasm-bindgen` warn that it could no longer read the WebAssembly features the module uses; its `--remove-name-section` and `--remove-producers-section` give the same size without that loss. `wasm-opt` (Binaryen) is left out: one tool more to install in the CI, for a few kilobytes of a website of 128 kB. In Chromium, the probe runs 72 million steps per second at **Instant** while the page keeps drawing at 60 frames per second. |
| Front-end tooling | npm, TypeScript in strict mode, `svelte-check`, ESLint and Prettier, Vitest for the tests of the interface; the application in `web/`, created by `sv create` (the official tool of Svelte), its scripts in TypeScript run by Node.js 24 without a build | npm comes with Node.js, already installed; the checks of the front-end run in the CI next to `cargo fmt`, Clippy and `cargo test`, and block a pull request the same way. The configuration of `sv create` is the one every Svelte developer knows (SvelteKit 3 holds it in `vite.config.ts`); Node.js 24 strips the types of a TypeScript script by itself, so the build script is typed like the rest without a tool more. |
| Continuous integration | The checks of Rust and those of the interface as separate jobs, after a job that lists the changed files (`dorny/paths-filter`); a pull request that changes only documentation skips them; a last job `CI`, always run, fails when one of them failed, and is the only check the ruleset requires | A workflow left out by its `paths` would leave the required checks waiting, and the pull request blocked, hence the jobs skipped instead. A skipped job counts as passed, even when skipped because the job that lists the files failed: the job `CI` looks at the result of each job, and lets the jobs be renamed without touching the ruleset. The interface is checked when the Rust code changes too, since it loads the core. |
| Deployment | GitHub Pages at `stepwise.sylent.tools`, published by a GitHub Actions workflow on every merge into `main`; the release workflow of the template removed | Free for a public repository, static, enough for an educational website; see [GitHub Pages usage](github-pages-usage.md). Version tags stay, to name the versions. |
