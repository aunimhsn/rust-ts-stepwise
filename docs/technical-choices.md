# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons.

| Topic | Choice | Reason |
|---|---|---|
| Language core | Lexer, parser, checker and interpreter of the learner's language in Rust, compiled to WebAssembly with `wasm-bindgen` | The owner's choice, and a language implementation is where Rust's enums and exhaustive matching help most. The whole core stays a plain Rust library, tested with `cargo test` without a browser; only a thin crate exposes it to JavaScript. |
| Execution | The interpreter runs one instruction per `step()` call, driven by the interface at each animation frame, a number of steps per frame set by the speed | An infinite loop of the learner never freezes the page: it keeps running visibly until **Stop**. The same mechanism gives the animation of the robot, the highlighted current line, the pause, the step button and the breakpoints. |
| No panic in the core | Clippy lints that forbid what can panic in the core (`unwrap`, `expect`, indexing, `panic!`), set up with the workspace | A panic aborts the WebAssembly module, and the page with it: every program of a learner, even absurd, must end with an error the interface can show. Taken from rust-exile-market, whose parser follows the same rule. |
| Interface | TypeScript with [Svelte](https://svelte.dev) 5 | A component holds its markup, script and style in one file with little boilerplate, so the repository reads easily; the runes (`$state`, `$derived`) make the reactive values explicit; compiled, with almost no runtime next to the WebAssembly module. React was rejected for its boilerplate and the pitfalls of its hooks, Vue for being a little more verbose, Solid for its smaller community. SvelteKit or Svelte with Vite alone: decided with the pages of the specifications. |
| Code editor | [CodeMirror 6](https://codemirror.net) | Every part of its look is set by our own CSS theme, and its extensions already cover what the editor needs: our highlighting (which can come from the Rust lexer), the errors underlined with their message, the current line highlighted, the breakpoints in the gutter, the automatic indentation, undo and search. Writing our own editor was rejected: weeks to reach a real editor (cursor, selection, undo, accents, accessibility) and many bugs, outside the subject of the project. Monaco was rejected: several megabytes and hard to take out of its VS Code look. The console, where the program writes, is our own Svelte component. |
| Interface translations | [Fluent](https://projectfluent.org) with `@fluent/bundle`, `locales/en.ftl` as the reference | English only in version 1, French possible later without touching the code. The core returns its errors as a code with its values and its position, never as a sentence, so that the error messages are translated with the rest of the interface. |
| Levels | JSON files with a format version: the terrain drawn as lines of text (one character per cell, with a legend), the robot, the items and the goals placed by coordinates (origin at the top left, `y` downward); read with `serde` and checked by the core | Read natively by Rust and TypeScript; the map is readable at a glance in the file and in Git diffs, and editable by hand. Everything by coordinates was rejected (unreadable past 10 × 10), as were a format of our own (one more parser), TOML (unsuited to grids) and RON (Rust only). |
| World elements | SVG drawings, designed one by one on a sheet of elements, then used as they are by the application | Sharp at every size and zoom; the drawings of the mock-up become the files of the application. Rendering the grid in SVG or in a canvas: decided with the size of the maps in the specifications. |
| Data | Everything in the browser: a static website, the progress in `localStorage` | No account and no server to run, keep or secure; the learners' data never leaves their browser. |
| Releases | GitHub Actions workflow triggered by version tags | Comes from the command-line template: a roadmap step replaces it with the deployment of the website. |
