# Technical choices

The technical choices of the [roadmap](../roadmap.md), with their reasons.

| Topic | Choice | Reason |
|---|---|---|
| Language core | Lexer, parser, checker and interpreter of the learner's language in Rust, compiled to WebAssembly with `wasm-bindgen` | The owner's choice, and a language implementation is where Rust's enums and exhaustive matching help most. The whole core stays a plain Rust library, tested with `cargo test` without a browser; only a thin crate exposes it to JavaScript. |
| Execution | The interpreter runs one instruction per `step()` call, driven by the interface at each animation frame, a number of steps per frame set by the speed | An infinite loop of the learner never freezes the page: it keeps running visibly until **Pause** or **Reset**. The same mechanism gives the animation of the robot, the highlighted current line, the pause, the step button and the breakpoints. |
| No panic in the core | Clippy lints that forbid what can panic in the core (`unwrap`, `expect`, indexing, `panic!`), set up with the workspace | A panic aborts the WebAssembly module, and the page with it: every program of a learner, even absurd, must end with an error the interface can show. Taken from rust-exile-market, whose parser follows the same rule. |
| Interface | TypeScript with [Svelte](https://svelte.dev) 5 | A component holds its markup, script and style in one file with little boilerplate, so the repository reads easily; the runes (`$state`, `$derived`) make the reactive values explicit; compiled, with almost no runtime next to the WebAssembly module. React was rejected for its boilerplate and the pitfalls of its hooks, Vue for being a little more verbose, Solid for its smaller community. |
| Pages | [SvelteKit](https://svelte.dev/docs/kit) with `adapter-static`, server-side rendering off, the pages prerendered as empty shells | The specifications have four kinds of pages (home, level, sandbox, manual), each with its own address so that the manual can be linked: SvelteKit gives the routing and the folder layout every Svelte developer knows, and builds a static website. Svelte with Vite and a router of our own was rejected: less code at first, but a structure of our own to explain. |
| Interpreter | A tree-walking interpreter with an explicit stack of frames (each frame: the block, the position in it, the variables), never the Rust call stack | Pausing between two steps, anywhere in nested loops and calls, needs the whole state of the program in data, and the variables panel reads that same data. The limit of 200 nested calls is the length of that stack: a recursion of the learner can't overflow the stack of the browser. |
| Lexer | Hand-written, line by line, in `crates/core/src/lexer.rs`: the indentation becomes `Indent` and `Dedent` tokens (four spaces more, or back to an enclosing line, anything else is an error that names the two closest levels); the comments are dropped; any word of letters, digits and underscores, in any alphabet, is a name; the first error stops it | A statement never spans two lines, so reading line by line is enough and keeps the lexer short; no generator (`logos`) for a few dozen tokens. Whether an indented line follows a `:` is left to the parser, which can then say that the `:` is missing on the line above rather than that the next line is indented. Names in any alphabet (`paintSide`, `côté`) are refused by the checker, which suggests the `snake_case` version, rather than by the lexer, which could only say that a character is unexpected. The highlighting of the editor is decided at step 15. |
| Parser | Hand-written, by recursive descent, in `crates/core/src/parser.rs`: one method per statement, and for the expressions a loop that climbs the priorities of the operators; the tree of `crates/core/src/ast.rs` keeps the span of every node; the first error stops it, the lexer's or its own, as one `SyntaxError`; the tree is at most 200 levels deep (parentheses, operators, calls and blocks), the height of each expression being counted as it is built | A language this small needs no generator, and a hand-written parser chooses its errors: `=` for `==`, chained comparisons, the words of other languages wherever they are. The depth is limited in the tree, not only in the recursions of the parser: a chain such as `1 + 1 + 1 + …` is parsed by a loop, yet gives a tree as deep as it is long, which would overflow the stack later, in the checker, the interpreter or when the tree is freed. What needs the names of the program (an expression alone on its line that isn't a call, a `break` outside a loop, a function in a block) is left to the checker, which gives every error rather than the first. Measured in the review of step 6a, at 199 levels: the parser alone needs between 64 and 128 KiB of the stack in a release WebAssembly module (between 256 and 512 KiB in a debug one), out of 1 MiB by default; the checker and the interpreter will walk the same tree, so the measure is redone at step 6b and tested through the real module at step 10. |
| Positions | A line and a column, both from 1, the column in characters (Unicode scalar values), at the start and the end of each token and error | The console shows a line and a column as a learner counts them, accents included. CodeMirror counts in UTF-16 code units, where an emoji takes two: the bridge converts with the source (step 10). |
| Numbers | `i64` with checked arithmetic (`checked_add`…), sent to the interface as text | An overflow becomes the error of the specifications instead of a panic or a wrong value; JavaScript numbers can't hold every `i64` exactly. |
| Code editor | [CodeMirror 6](https://codemirror.net) | Every part of its look is set by our own CSS theme, and its extensions already cover what the editor needs: our highlighting (which can come from the Rust lexer), the errors underlined with their message, the current line highlighted, the breakpoints in the gutter, the automatic indentation, undo and search, and the command menu of Ctrl+Space (its `autocomplete` extension groups the suggestions in sections, shows a description next to each, and inserts snippets with fields to fill in). Writing our own editor was rejected: weeks to reach a real editor (cursor, selection, undo, accents, accessibility) and many bugs, outside the subject of the project. Monaco was rejected: several megabytes and hard to take out of its VS Code look. The console, where the program writes, is our own Svelte component. |
| Interface translations | [Fluent](https://projectfluent.org) with `@fluent/bundle`, `locales/en.ftl` as the reference | English only in version 1, French possible later without touching the code. The core returns its errors as a code with its values and its position, never as a sentence, so that the error messages are translated with the rest of the interface. |
| Manual | One Markdown file per section and per language (`manual/en/`), turned into pages when the website is built | Long texts with examples read and change better as Markdown than as Fluent messages; a French manual is another folder. The examples are checked by the tests with the real parser, so that the manual never shows code Stepwise refuses. |
| Levels | JSON files with a format version: the terrain drawn as lines of text (one character per cell, with a legend), the robot, the items and the goals placed by coordinates (origin at the top left, `y` downward); read with `serde` and checked by the core; the texts of a level (title, goal, hint) are Fluent messages, named after the level | Read natively by Rust and TypeScript; the map is readable at a glance in the file and in Git diffs, and editable by hand. Everything by coordinates was rejected (unreadable past 10 × 10), as were a format of our own (one more parser), TOML (unsuited to grids) and RON (Rust only). Every level file is checked by `cargo test`, which also runs a solution of each variant. |
| World elements | SVG drawings, designed one by one on a sheet of elements, then used as they are by the application: one file per element in `docs/mockups/world-elements/daylight/`, stacked in each cell (the floor or the wall with its rim and its edge, the paint, the goal marks, the item, the robot turned to its direction with the item in its bay, its pincer and its eyes, the flag of a goal not met); only the paint strokes, which depend on the painted passages, are drawn by the map, in the shades of [Look of the world](../specs.md#look-of-the-world) | Sharp at every size and zoom; the drawings of the mock-up become the files of the application. The map is drawn in SVG too, one Svelte component per element: a map has at most 16 × 12 cells, a few hundred shapes, far below what makes SVG slow; the moves are CSS transitions. A canvas was rejected: it would redraw by hand what SVG and CSS give, and blur at some zooms unless handled. Small files stacked, rather than one drawing per state (a robot carrying, a robot lit…), keep the number of files small and let the animations move each part on its own. |
| Font of the name | Fredoka 600, under the SIL Open Font License, bundled with the application rather than loaded from Google Fonts | Its round shapes answer the corners of the robot and the round ends of the paint. Bundled, the website loads no font from another server, and works the same offline. The fonts of the interface come with the design system. |
| Data | Everything in the browser: a static website, the progress in `localStorage` | No account and no server to run, keep or secure; the learners' data never leaves their browser. |
| WebAssembly build | `cargo build --target wasm32-unknown-unknown`, then the `wasm-bindgen` command-line tool at the exact version of the `wasm-bindgen` crate, from an npm script | The rustwasm organization was wound down in 2025 ([Rust blog](https://blog.rust-lang.org/inside-rust/2025/07/21/sunsetting-the-rustwasm-github-org)): `wasm-bindgen` moved to its own organization and goes on, while `wasm-pack` passed to a single maintainer. Calling `wasm-bindgen` directly avoids depending on `wasm-pack`, with one command more. Checked again on 2026-11-10 (step 4b): `wasm-bindgen` 0.2.130 is its latest version, and `wasm-pack` is still released (0.15.1), but the direct call is kept: one tool less, and `web/scripts/build-wasm.ts` checks the version of the tool against the one of the crate, given by `cargo pkgid`, before building. The glue is generated with `--target web`: Vite loads the module as any other file, without a plugin. |
| WebAssembly size | The release profile at the default `opt-level` 3, with `lto` and one codegen unit, not stripped by Cargo; `wasm-bindgen` removes the name and producers sections | Measured on 2026-11-10 (step 4c) on the probe, after `wasm-bindgen`, with the speed of `step()` called in a loop from Node.js 24: `opt-level` 3 gives 16.3 kB (7.3 kB gzipped) and 206 million steps per second, `"s"` 17.9 kB (7.8 kB) and 186 million, `"z"` 18.1 kB (8.0 kB) and 120 million. On a code this small, 3 is both the smallest and the fastest: it inlines and then removes what `"s"` and `"z"` keep as calls. `strip = true` made `wasm-bindgen` warn that it could no longer read the WebAssembly features the module uses; its `--remove-name-section` and `--remove-producers-section` give the same size without that loss. `wasm-opt` (Binaryen) is left out: one tool more to install in the CI, for a few kilobytes of a website of 128 kB. In Chromium, the probe runs 72 million steps per second at **Instant** while the page keeps drawing at 60 frames per second. |
| Front-end tooling | npm, TypeScript in strict mode, `svelte-check`, ESLint and Prettier, Vitest for the tests of the interface; the application in `web/`, created by `sv create` (the official tool of Svelte), its scripts in TypeScript run by Node.js 24 without a build | npm comes with Node.js, already installed; the checks of the front-end run in the CI next to `cargo fmt`, Clippy and `cargo test`, and block a pull request the same way. The configuration of `sv create` is the one every Svelte developer knows (SvelteKit 3 holds it in `vite.config.ts`); Node.js 24 strips the types of a TypeScript script by itself, so the build script is typed like the rest without a tool more. |
| Continuous integration | The checks of Rust and those of the interface as separate jobs, after a job that lists the changed files (`dorny/paths-filter`); a pull request that changes only documentation skips them; a last job `CI`, always run, fails when one of them failed, and is the only check the ruleset requires | A workflow left out by its `paths` would leave the required checks waiting, and the pull request blocked, hence the jobs skipped instead. A skipped job counts as passed, even when skipped because the job that lists the files failed: the job `CI` looks at the result of each job, and lets the jobs be renamed without touching the ruleset. The interface is checked when the Rust code changes too, since it loads the core. |
| Deployment | GitHub Pages at `stepwise.sylent.tools`, published by a GitHub Actions workflow on every merge into `main`; the release workflow of the template removed | Free for a public repository, static, enough for an educational website; see [GitHub Pages usage](github-pages-usage.md). Version tags stay, to name the versions. |
